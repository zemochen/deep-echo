# 前后端分离架构重构 - 需求文档

## 简介

DeepEcho系统从单体Python桌面应用重构为前后端分离架构。采用Tauri框架作为中间层，实现TypeScript/React前端与Python后端服务的解耦。前端负责UI渲染和用户交互，后端保持现有AI服务功能，通过Tauri命令层实现零延迟的进程间通信。

## 术语表

- **前端应用**: 基于React的TypeScript用户界面，运行在Tauri窗口中
- **Tauri命令层**: Rust编写的进程间通信层，负责前后端交互
- **后端服务**: Python编写的AI处理服务，包含音频处理、转录、AI响应等核心功能
- **IPC通信**: 进程间通信，通过Tauri命令实现前后端数据交互
- **Web Audio API**: 浏览器原生音频采集接口
- **系统资源访问**: 通过Tauri访问系统级资源（文件、设备等）
- **实时通信**: 前后端之间的低延迟数据传输

## 需求

### 需求1：前端用户界面

**用户故事：** 作为用户，我希望通过现代化的Web UI与系统交互，以便获得更好的用户体验和跨平台兼容性。

#### 验收标准

1. 当应用启动时，前端应显示包含转录区域、响应区域和控制面板的主界面
2. 当音频被转录时，前端应实时更新转录显示区域
3. 当AI生成响应时，前端应实时更新响应显示区域
4. 前端应提供冻结/解冻按钮来暂停显示更新
5. 前端应提供可配置的更新间隔滑块来控制响应生成频率
6. 前端应提供AI厂商选择下拉菜单来切换AI提供商
7. 前端应提供清除上下文按钮来重置转录和响应历史
8. 前端应显示当前系统状态（就绪、处理中、错误等）

### 需求2：Tauri命令层架构

**用户故事：** 作为系统架构师，我希望通过Tauri命令层实现前后端的解耦，以便支持多种客户端和部署方式。

#### 验收标准

1. 当前端调用Tauri命令时，命令层应将请求转发到Python后端服务
2. 当Python后端返回结果时，命令层应将结果返回给前端
3. 命令层应支持异步命令处理以避免阻塞UI
4. 命令层应实现错误处理和异常转发机制
5. 命令层应支持事件监听，允许后端主动推送数据到前端
6. 命令层应提供系统资源访问接口（文件、设备等）
7. 命令层应实现请求超时和重试机制

### 需求3：前后端通信协议

**用户故事：** 作为开发者，我希望有清晰的通信协议定义，以便前后端能够正确交互。

#### 验收标准

1. 当前端需要启动音频录制时，应通过Tauri命令调用后端的start_recording接口
2. 当前端需要停止音频录制时，应通过Tauri命令调用后端的stop_recording接口
3. 当前端需要获取转录结果时，应通过Tauri命令调用后端的get_transcript接口
4. 当前端需要生成AI响应时，应通过Tauri命令调用后端的generate_response接口
5. 当前端需要切换AI厂商时，应通过Tauri命令调用后端的switch_provider接口
6. 当后端有新的转录数据时，应通过事件推送到前端
7. 当后端有新的AI响应时，应通过事件推送到前端
8. 所有通信数据应使用JSON格式序列化

### 需求4：Python后端服务

**用户故事：** 作为系统维护者，我希望Python后端保持现有功能，以便最小化重构工作量。

#### 验收标准

1. 当Tauri命令调用后端接口时，后端应执行相应的音频处理、转录或AI响应生成
2. 后端应保持现有的多线程架构和错误处理机制
3. 后端应支持多个AI厂商的切换
4. 后端应通过事件系统将结果推送给Tauri命令层
5. 后端应支持配置文件管理和API密钥存储
6. 后端应实现资源优化和内存管理
7. 后端应提供系统诊断和日志功能

### 需求5：音频采集方案

**用户故事：** 作为用户，我希望系统能够采集麦克风和扬声器音频，以便转录完整的对话。

#### 验收标准

1. 当应用启动时，后端应检测并连接到默认麦克风设备
2. 当应用启动时，后端应检测并连接到默认扬声器输出设备（Windows使用WASAPI loopback，macOS使用BlackHole）
3. 当从任一音频源检测到音频时，后端应持续将音频数据流传输到处理队列
4. 当没有可用的默认音频设备时，后端应显示错误消息并优雅地处理故障
5. 后端应支持Windows和macOS操作系统的音频采集
6. 前端应通过Tauri命令获取可用的音频设备列表
7. 前端应提供音频设备选择界面

### 需求6：系统资源访问

**用户故事：** 作为系统，我希望通过Tauri访问系统级资源，以便支持文件操作和设备管理。

#### 验收标准

1. 当需要读取配置文件时，Tauri应通过文件系统API访问本地文件
2. 当需要保存日志时，Tauri应通过文件系统API写入本地文件
3. 当需要访问系统设备时，Tauri应提供设备列表接口
4. 当需要访问系统信息时，Tauri应提供系统信息接口
5. Tauri应实现文件访问权限控制
6. Tauri应实现安全的文件路径处理

### 需求7：实时数据推送

**用户故事：** 作为用户，我希望系统能够实时推送转录和响应结果，以便获得即时反馈。

#### 验收标准

1. 当后端完成转录时，应立即通过事件推送到前端
2. 当后端生成AI响应时，应立即通过事件推送到前端
3. 当系统状态变化时，应通过事件推送到前端
4. 前端应能够监听和处理这些事件
5. 事件推送应支持多个监听器
6. 事件推送应保证消息不丢失

### 需求8：错误处理和恢复

**用户故事：** 作为用户，我希望系统能够优雅地处理错误，以便在出现问题时能够继续使用。

#### 验收标准

1. 当Tauri命令执行失败时，应返回清晰的错误信息
2. 当后端服务不可用时，前端应显示错误提示
3. 当网络连接中断时，系统应尝试重新连接
4. 当音频设备不可用时，系统应提示用户
5. 系统应实现自动重试机制
6. 系统应记录所有错误日志

### 需求9：配置管理

**用户故事：** 作为用户，我希望能够配置系统参数，以便根据需要调整系统行为。

#### 验收标准

1. 当应用启动时，应加载配置文件中的设置
2. 前端应提供配置界面来修改系统参数
3. 当用户修改配置时，应保存到配置文件
4. 系统应支持多个配置预设
5. 系统应验证配置参数的有效性
6. 系统应支持配置导入和导出

### 需求10：跨平台兼容性

**用户故事：** 作为用户，我希望系统能够在Windows和macOS上运行，以便支持更多用户。

#### 验收标准

1. 前端应使用跨平台兼容的Web技术
2. Tauri应支持Windows和macOS平台
3. 后端应保持现有的跨平台支持
4. 系统应处理平台特定的差异
5. 系统应在两个平台上提供一致的用户体验
6. 系统应支持平台特定的功能（如系统托盘）

### 需求11：性能优化

**用户故事：** 作为用户，我希望系统能够高效运行，以便不影响计算机的其他应用。

#### 验收标准

1. 前端应使用高效的渲染和更新机制
2. Tauri命令层应实现异步处理以避免阻塞
3. 后端应保持现有的性能优化
4. 系统应监控内存和CPU使用情况
5. 系统应在空闲时最小化资源使用
6. 系统应支持性能监控和诊断

### 需求12：开发和部署

**用户故事：** 作为开发者，我希望有清晰的开发和部署流程，以便快速迭代和发布。

#### 验收标准

1. 项目应有清晰的目录结构和模块组织
2. 应提供开发环境配置指南
3. 应提供构建和打包脚本
4. 应支持本地开发和调试
5. 应支持自动化测试
6. 应提供部署和发布指南
